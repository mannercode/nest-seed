# 인증

현재 Argon2id 비밀번호 비교, 역할별 JWT, Redis refresh 토큰 회전·폐기, IP별 로그인 실패 제한, BFF 쿠키 처리가 있다. 기존 계정·해시의 마이그레이션은 시드의 작업 범위에 포함하지 않는다.

## 재현한 문제

### A2. 계정 변경과 세션 폐기의 경합·부분 실패

- [ ] 비밀번호 변경·계정 삭제와 로그인 발급이 겹치거나 세션 폐기가 실패해도, 변경 전 인증으로 refresh 세션을 계속 사용할 수 없게 한다.

근거: [UsersService](../apps/api/src/services/core/users/users.service.ts)와 [AdminsService](../apps/api/src/services/core/admins/admins.service.ts)는 DB 변경 후 세션을 폐기한다. 로그인은 계정 조회·비밀번호 비교 후 별도로 세션을 만든다. refresh는 현재 계정 상태를 조회하지 않는다.

사용자 서비스와 실제 MongoDB·Redis를 사용해 다음 네 경우를 재현했다. 관리자도 같은 처리 순서이지만 관리자 경합·장애는 별도로 실행하지 않았다.

| 조건                                                                     | 관찰한 결과                                                                |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 비밀번호 검증 후 토큰 발급을 멈추고, 비밀번호 변경을 완료한 뒤 발급 재개 | 이전 비밀번호로 검증한 요청이 새 세션을 발급하고 refresh HTTP 200          |
| 같은 순서에서 계정 삭제를 완료한 뒤 발급 재개                            | 삭제된 사용자의 새 세션으로 refresh HTTP 200                               |
| 비밀번호 DB 변경 후 `revokeAllSessions`가 한 번 실패하도록 주입          | 변경 요청은 실패하지만 새 비밀번호가 저장되고 이전 세션은 refresh HTTP 200 |
| 계정 DB 삭제 후 같은 실패 주입                                           | 삭제 요청은 실패하지만 계정은 삭제되고 이전 세션은 refresh HTTP 200        |

최소 범위: A3에서 회수 완료 기준과 저장소 장애 시 동작을 정한다. 계정의 인증 버전을 DB 변경과 함께 갱신하고 발급·refresh에서 확인하는 방식을 우선 검토한다. 데이터 모델과 저장소 조회가 추가되므로 확정 후 구현한다. [공통 세션 서비스](../libs/common/src/auth/jwt-auth.service.ts)는 전체 회수 시 조회한 세션만 지우고 이후 생성된 세션은 보존하는 계약이므로, 앱의 계정 변경 보장과 구분한다. 단순히 Redis 삭제를 한 번 더 호출하는 것으로 경합·부분 실패를 해결했다고 보지 않는다.

검증: 사용자·관리자 각각에서 위 실행 순서를 제어하고 변경 전·후 세션의 refresh 결과를 확인한다. 전체 로그아웃과 새 로그인의 경합, 회수 재요청, 기존 refresh 회전 대 로그아웃 검증도 포함한다. 관리자 삭제는 HTTP에 노출되지 않은 서비스 동작임을 구분한다.

### A6. BFF 인증 경로와 HTTP 메서드 판별

- [ ] API가 같은 인증 경로로 처리하는 요청에 BFF의 역할 제한·토큰 쿠키 처리를 일관되게 적용하고, POST 외 요청이 로그아웃 처리를 수행하지 않게 한다.

근거: [사용자 BFF](../apps/user-app/src/app/api/[...path]/route.ts)와 [관리자 BFF](../apps/console/src/app/api/[...path]/route.ts)는 경로를 대소문자로 구분하지만 API 라우터는 구분하지 않는다. `isLogin`·`isLogout`은 HTTP 메서드를 검사하지 않는다.

실제 API·사용자 BFF의 production 빌드에서 다음을 재현했다. 관리자 BFF도 역할 이름을 제외하면 같은 구현이지만 같은 변형 요청을 별도로 실행하지 않았다.

| 요청                                                 | 관찰한 결과                                                    |
| ---------------------------------------------------- | -------------------------------------------------------------- |
| 유효한 사용자 자격 증명으로 `POST /api/Users/Login`  | 쿠키 설정과 HTTP 204 대신 HTTP 200과 토큰 JSON 반환            |
| 유효한 관리자 자격 증명으로 `POST /api/ADMINS/LOGIN` | 다른 역할의 인증 경로 차단을 우회하고 토큰 JSON 반환           |
| 유효한 refresh 토큰으로 `POST /api/Users/Refresh`    | 외부 refresh 경로 차단을 우회하고 토큰 JSON 반환               |
| 로그인한 브라우저에서 `GET /api/users/logout`        | HTTP 502를 반환하면서 쿠키 삭제; API 세션 폐기는 실행하지 않음 |

영향: 인증에 성공할 자격 증명이나 토큰이 필요하지만, BFF의 토큰 비노출·역할별 인증 경로 계약을 어긴다. GET 요청은 로그아웃에 필요한 세션 폐기 없이 브라우저 로그인 상태를 바꾼다.

최소 범위: 인증 경로 판별을 API의 대소문자 처리와 맞추고, 로그인·로그아웃 처리를 POST로 한정한다. 일반 자원 ID를 소문자로 바꾸거나 두 BFF를 새 공통 계층으로 옮길 필요는 없다.

검증: 두 BFF에서 정상·혼합 대소문자 경로, 다른 역할의 인증 경로, 직접 refresh, GET·HEAD 로그아웃을 요청한다. 상태 코드뿐 아니라 응답의 토큰 포함 여부, 쿠키 변경과 서버 세션 폐기를 확인한다.

### A7. 관리자 로그아웃의 통신 실패 표시

- [ ] 브라우저에서 BFF로 로그아웃 요청을 보내지 못했을 때 실패를 표시하고 재시도할 수 있게 한다.

근거: [LogoutButton](../apps/console/src/app/_components/logout-button.tsx)은 모든 오류를 무시하고 로그인 화면으로 이동한다. Playwright에서 `/api/admins/logout` 요청을 중단했을 때 로그인 화면으로 이동했지만 refresh 쿠키가 남고 오류 안내가 없는 것을 재현했다. BFF가 응답하기 전에 실패하면 BFF의 쿠키 삭제는 실행되지 않는다.

최소 범위: 통신 실패를 성공한 로그아웃처럼 표시하지 않는다. BFF에 도달한 뒤 API 호출이 실패하면 쿠키를 지우는 기존 동작과 구분하고, 실제 로그아웃 완료 여부를 사용자에게 알린다. 임의 재시도로 실패를 숨기지 않는다.

검증: 브라우저→BFF 통신 실패, BFF→API 실패, 정상 로그아웃 각각에서 오류 안내·쿠키·화면 이동·재시도를 확인한다.

## 결정 필요

### A1. 비밀번호 입력 정책

- [ ] 최소·최대 길이와 문자 수 계산·공백 처리 방식을 정하고 생성·변경·로그인·복구에 적용한다.

근거: 사용자·관리자 생성·변경 DTO와 [관리자 생성 스크립트](../apps/api/scripts/admin-create.cjs)는 최소 1자만 검사하고 로그인 DTO는 문자열 여부만 검사한다. [PasswordHasher](../libs/common/src/auth/password.ts)는 Argon2id로 원문 전체를 처리하므로 bcrypt의 72바이트 한도를 입력 정책으로 사용할 이유는 없다.

최소 범위: HTTP 본문 크기 제한과 비밀번호 최대 길이를 구분하고, 입력을 조용히 자르거나 trim하지 않는다. 가입 화면·DTO·독립 관리자 스크립트에 같은 정책을 적용한다. 앱의 가입 정책을 재사용 해시 함수에 강제하지 않는다. 이메일 식별은 [사용자 U2](users.md)와 함께 결정한다.

검증: ASCII·한글·이모지·공백의 경계값과 생성·로그인·변경 간 일관성을 확인한다. 허용된 긴 비밀번호의 끝부분까지 비교하는 기존 테스트를 유지한다.

### A3. 토큰·세션의 유효 기간과 회수 보장

- [ ] 로그아웃·비밀번호 변경·계정 정지·탈퇴의 효력 시점과 refresh 재사용 정책을 정하고 API·BFF·설정·문서를 맞춘다.

근거: [현재 계약](../apps/README.md#http와-인증-계약)은 access JWT를 최대 5분간 허용하며 계정 상태를 매 요청 조회하지 않는다. refresh 유효 기간은 현재 설정에서 7일이며 갱신할 때마다 연장되어 별도의 세션 최대 수명은 없다. 회전된 refresh 토큰은 409이고 현재 세션을 폐기하지 않는다. 관리자 HTTP에는 사용자와 같은 전체 로그아웃 경로가 없다. 이 동작들은 A2의 회수 누락과 구분해 정책으로 판단한다.

최소 범위: access 즉시 회수 여부, refresh 갱신을 포함한 세션 최대 수명, 관리자 전체 로그아웃 제공 여부를 정한다. 즉시 회수를 선택하면 상태 조회 비용과 저장소 장애 시 동작을 함께 결정한다. 토큰 재사용 탐지를 바꾸면 정상적인 동시 요청·BFF 재시도와의 구분을 포함한다.

검증: 사용자·관리자 각각의 만료·회수·동시 갱신, BFF의 쿠키 갱신과 오류 응답이 같은 계약을 따른다. 기존의 5분 허용·409 기대값은 계약 변경을 결정한 경우에만 바꾼다.

### A4. 로그인 실패 제한과 실제 클라이언트 IP

- [ ] IP·계정별 제한의 조합, 한도·만료·해제 조건, 사용자·관리자 제한 공유 여부를 정하고 적용한다.

근거: [LoginRateLimiterService](../apps/api/src/services/gateway/login-rate-limiter.service.ts)는 IP만 집계하고 성공해도 초기화하지 않는다. 현재 한도는 실패 50회이며 첫 실패부터 15분 뒤 만료된다. 두 역할이 같은 집계를 사용한다. [BFF 기본 설정](../apps/README.md#데모와-bff)에서는 여러 사용자가 BFF 주소 하나로 보일 수 있다. 브라우저 테스트의 신뢰 헤더 설정은 실제 배포 edge의 신뢰 경로를 검증하지 않는다.

최소 범위: 같은 IP를 쓰는 정상 사용자와 여러 IP에서 같은 계정으로 시도하는 요청을 함께 고려한다. 계정 제한을 추가하면 타인의 반복 실패로 잠긴 계정의 해제 경로도 정한다. 실제 배포 경로에서 IP를 누가 확정하고 어떤 프록시를 신뢰할지 정해 API·BFF·설정을 일치시킨다.

검증: 같은 IP의 다른 계정, 다른 IP의 같은 계정, 존재하지 않는 계정, 동시 실패, 만료 후 로그인, Redis 장애를 확인한다. 프록시 신뢰를 사용할 경우 위조·누락된 전달 헤더와 실제 edge 경로를 구분해 검증한다.

### A5. 비밀번호 변경·복구

- [ ] 로그인 상태의 비밀번호 변경과 비밀번호 분실 복구를 별도 흐름으로 정하고 구현한다.

근거: 현재 본인·관리자 수정 DTO에 새 비밀번호를 넣을 수 있지만 현재 비밀번호 확인과 분실 복구 경로는 없다.

최소 범위: 본인 변경의 재인증, 관리자에 의한 변경 허용 여부, 복구 토큰의 일회성·만료·재발급, 복구 후 기존 세션 처리를 정한다. [사용자 U3](users.md)의 이메일 확인·실제 발송 수단과 연계한다. 미등록 계정의 응답과 재발송 제한도 합의한 정책으로 구현한다.

검증: 정상 변경·복구, 틀린 현재 비밀번호, 만료·재사용·동시 사용된 복구 토큰, 발송 실패, 복구 후 이전 비밀번호와 세션의 동작을 확인한다.

검증 위치: [JWT 세션 테스트](../libs/common/src/auth/__tests__/jwt-auth.service.spec.ts), [user-auth.spec.ts](../apps/api/src/__tests__/core/user-auth.spec.ts), [admin-auth.spec.ts](../apps/api/src/__tests__/core/admin-auth.spec.ts), [관리자 브라우저 흐름](../tests/web/e2e/console-auth-flow.spec.ts), [사용자 브라우저 흐름](../tests/web/e2e/user-auth-flow.spec.ts).
