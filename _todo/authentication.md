# 인증

현재 bcrypt 비밀번호 비교, 역할별 JWT, Redis refresh 토큰 회전·폐기, IP별 로그인 실패 제한, BFF 쿠키 처리가 있다. 이미 구현한 흐름을 유지하면서 아래 경계와 정책을 보완한다.

## 검증·수정 우선

### A1. 비밀번호 입력과 해시의 길이 경계

- [ ] bcrypt의 입력 경계와 기존 비밀번호 호환을 고려해 비밀번호 길이 계약을 정하고 생성·변경·로그인·복구에 적용한다.

근거: [PasswordHasher](../libs/common/src/auth/password.ts)는 bcrypt에 원문을 전달하고, 사용자·관리자 생성 DTO와 [관리자 생성 스크립트](../apps/api/scripts/admin-create.cjs)는 최소 1자만 검사한다. 설치된 bcrypt에서 `a` 72개 뒤에 서로 다른 문자열을 붙인 두 비밀번호가 같은 해시와 일치하는 것을 로컬 실행으로 재현했다. HTTP 전체 흐름은 아직 재현하지 않았다.

최소 범위: UTF-8 바이트 경계와 문자 길이를 구분하고, 기존 장문 비밀번호 사용자의 로그인·변경 방법을 정한다. 비밀번호를 조용히 잘라내지 않는다. 최소 길이·해시 비용·알고리즘 교체는 정책 결정으로 분리하며, 공유 라이브러리의 소비자와 독립 관리자 스크립트에도 같은 계약을 반영한다.

검증: ASCII·한글·이모지의 경계값, 경계 뒤만 다른 비밀번호, 기존 해시의 로그인·변경을 확인한다. [기존 PasswordHasher 테스트](../libs/common/src/auth/__tests__/guards.spec.ts)와 API 테스트를 함께 갱신한다.

### A2. 계정 변경과 세션 폐기의 경합·부분 실패

- [ ] 로그인 발급·전체 로그아웃·비밀번호 변경·계정 삭제 사이의 경합과 MongoDB 성공 후 Redis 실패를 재현하고 회수 계약의 불일치를 수정한다.

근거: [UsersService](../apps/api/src/services/core/users/users.service.ts)와 [AdminsService](../apps/api/src/services/core/admins/admins.service.ts)는 DB 변경 후 세션을 폐기한다. 로그인은 계정 조회·비밀번호 비교 후 별도로 세션을 만든다. [JwtAuthService](../libs/common/src/auth/jwt-auth.service.ts)의 전체 회수는 조회한 세션만 지우며 조회 뒤 생성된 세션을 보존한다.

최소 범위: 변경 전 비밀번호 검증을 끝낸 로그인이 변경 뒤 세션을 발급하는 경우, DB 변경 뒤 회수 실패, 회수 재요청을 확인한다. A3에서 회수 완료 기준을 정하고 복구 가능하게 만든다. 공통 세션 라이브러리의 기존 새 로그인 보존 계약을 앱의 계정 변경 정책과 구분한다.

검증: 실행 순서를 제어해 경합을 재현하고, 응답뿐 아니라 기존·신규 토큰으로 갱신 가능한 세션까지 확인한다. 기존 refresh 회전 대 로그아웃 검증은 유지한다.

## 결정 필요

### A3. 토큰·세션의 유효 기간과 회수 보장

- [ ] 로그아웃·비밀번호 변경·계정 정지·탈퇴의 효력 시점과 refresh 재사용 정책을 정하고 API·BFF·설정·문서를 맞춘다.

근거: [현재 계약](../docs/apps.md#http와-인증-계약)은 access JWT를 최대 5분간 허용하며 계정 상태를 매 요청 조회하지 않는다. 회전된 refresh 토큰은 409이고 현재 세션을 폐기하지 않는다. 관리자 HTTP에는 사용자와 같은 전체 로그아웃 경로가 없다.

최소 범위: access 즉시 회수 여부, refresh 갱신을 포함한 세션 최대 수명, 관리자 전체 로그아웃 제공 여부를 정한다. 즉시 회수를 선택하면 상태 조회 비용과 저장소 장애 시 동작을 함께 결정한다. 토큰 재사용 탐지를 바꾸면 정상적인 동시 요청·BFF 재시도와의 구분 및 기존 세션 전환을 포함한다.

검증: 사용자·관리자 각각의 만료·회수·동시 갱신, BFF의 쿠키 갱신과 오류 응답이 같은 계약을 따른다. 기존의 5분 허용·409 기대값은 계약 변경을 결정한 경우에만 바꾼다.

### A4. 로그인 실패 제한과 실제 클라이언트 IP

- [ ] IP·계정별 제한의 조합, 한도·만료·해제 조건, 사용자·관리자 제한 공유 여부를 정하고 적용한다.

근거: [LoginRateLimiterService](../apps/api/src/services/gateway/login-rate-limiter.service.ts)는 IP만 집계하고 성공해도 초기화하지 않는다. 두 역할이 같은 집계를 사용한다. [BFF 기본 설정](../docs/apps.md#데모와-bff)에서는 여러 사용자가 BFF 주소 하나로 보일 수 있다.

최소 범위: 같은 IP를 쓰는 정상 사용자와 여러 IP에서 같은 계정으로 시도하는 요청을 함께 고려한다. 계정 제한을 추가하면 타인의 반복 실패로 잠긴 계정의 해제 경로도 정한다. 실제 배포 경로에서 IP를 누가 확정하고 어떤 프록시를 신뢰할지 정해 API·BFF·설정을 일치시킨다.

검증: 같은 IP의 다른 계정, 다른 IP의 같은 계정, 존재하지 않는 계정, 동시 실패, 만료 후 로그인, Redis 장애를 확인한다. 프록시 신뢰를 사용할 경우 위조·누락된 전달 헤더와 실제 edge 경로를 구분해 검증한다.

### A5. 비밀번호 변경·복구

- [ ] 로그인 상태의 비밀번호 변경과 비밀번호 분실 복구를 별도 흐름으로 정하고 구현한다.

근거: 현재 본인·관리자 수정 DTO에 새 비밀번호를 넣을 수 있지만 현재 비밀번호 확인과 분실 복구 경로는 없다.

최소 범위: 본인 변경의 재인증, 관리자에 의한 변경 허용 여부, 복구 토큰의 일회성·만료·재발급, 복구 후 기존 세션 처리를 정한다. [사용자 U3](users.md)의 이메일 확인·실제 발송 수단과 연계한다. 미등록 계정의 응답과 재발송 제한도 합의한 정책으로 구현한다.

검증: 정상 변경·복구, 틀린 현재 비밀번호, 만료·재사용·동시 사용된 복구 토큰, 발송 실패, 복구 후 이전 비밀번호와 세션의 동작을 확인한다.

검증 위치: [JWT 세션 테스트](../libs/common/src/auth/__tests__/jwt-auth.service.spec.ts), [user-auth.spec.ts](../apps/api/src/__tests__/core/user-auth.spec.ts), [admin-auth.spec.ts](../apps/api/src/__tests__/core/admin-auth.spec.ts), [관리자 브라우저 흐름](../tests/web/e2e/console-auth-flow.spec.ts), [사용자 브라우저 흐름](../tests/web/e2e/user-auth-flow.spec.ts).
