# 실행 환경·설정·문서 — 미결 검토

[README의 시드 기준](../../README.md#기능코드-변경-시-주의사항)에 따라 사용 목적이나 비용 판단이 남은 항목만 둔다. 아래 항목을 새 기능이나 설정 변경으로 자동 전환하지 않는다.

## S1 — 개발 환경의 개인 도구 설정

[devcontainer.json](../../.devcontainer/devcontainer.json) 28–39행은 Codex·GitHub CLI의 호스트 설정과 Codex 상태 디렉터리를 기본으로 마운트한다. 현재 개발자의 작업 방식에는 맞고 필요한 디렉터리도 생성한다. 다만 처음 포크하는 사람은 NestJS 실행과 별개인 도구 설정까지 읽게 된다.

NestJS 시드의 핵심 실행에는 필요하지 않은 편의 설정이다. 현재 도구를 쓰는 사람에게는 가치가 있으므로 기본 제공 대상으로 삼을 도구의 범위를 먼저 정해야 한다. 분리한다면 개인 도구 마운트·링크로 한정하고, 이를 위해 새 설정 계층이나 별도 개발 경로를 만들지는 않는다.

## S2 — 재사용 조건을 찾는 진입점

[루트 manifest](../../package.json)에는 `license: MIT`가 있지만 루트에는 독립 `LICENSE`가 없다. 외부에 시드를 배포할 목적이라면 작성자가 의도한 라이선스 원문과 표시 정보를 확인할 위치를 마련하는 편이 명확하다. 작성자·권리 정보를 추정해서 문서를 생성하지 않았으며, 법적 적합성을 판정한 결과도 아니다.

## S3 — 실행 부담과 변경 범위

MongoDB의 transaction·majority, Redis의 hash slot, S3 업로드, NATS 전달, Restate 재실행은 예제의 실제 계약과 연결돼 있다. 단일 Dev Container 경로도 환경별 차이와 지원할 실행 경로를 줄이는 선택이다. 이런 역할은 구성을 두는 근거지만, 모든 규모와 실행 비용을 정당화하지는 않는다.

MongoDB 3노드·Redis 3노드·4개 API 복제본의 자원 사용량, 최초 준비 시간, 반복 CI의 추가 결함 발견 효과는 측정하지 않았다. Dev Container 시작마다 데이터를 초기화하는 제약도 문서화 여부와 별개로 포크 후 개발에 주는 부담을 평가해야 한다. README의 CRUD부터 읽는 순서는 탐색을 돕지만 설치·실행 비용을 줄이지 않는다. 따라서 시드에 과한지 부족한지에 대한 이 부분의 판단은 남아 있다. 재검토한다면 기존 보장을 유지하면서 비용과 효과를 먼저 비교하고, 횟수 축소나 별도 경량 실행 모드를 결론으로 미리 정하지 않는다.
