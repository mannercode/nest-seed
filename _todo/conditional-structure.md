# 조건문으로 합친 실행 절차

기준 커밋은 `63f250b03794af9f7cb9ac61bbacdb287c35234b`다. 미커밋·미추적 파일이 없는 상태에서, 서로 다른 동작을 라벨·모드·조건식으로 합쳐 읽기 어렵게 만든 부분을 검토했다. 아래 항목은 가독성과 수정 부담에 관한 발견이며 새 실행 오류를 재현한 결과는 아니다.

## 진행 대상

### C1. MongoDB fixture의 장애 준비 절차 분리

- [ ] [crud.repository.spec.ts](../libs/common/src/mongodb/__tests__/crud.repository.spec.ts)의 23행부터 시작하는 세 실패 사례를 각각의 `describe`로 나눈다.

조건·근거: `stage`가 `connect`, `index`, `cleanup`일 때 같은 `beforeEach`가 연결 직후 예외, 인덱스 초기화 예외, 연결 종료 예외를 선택한다. 41·44·50행의 조건을 함께 읽어야 한 사례에서 어떤 spy가 실제로 실패하는지 알 수 있다.

영향: 실패 지점과 원래 오류를 보존하는 조건을 수정할 때 다른 사례의 준비 절차까지 추적해야 한다. 현재 단언이 잘못 통과하거나 운영 동작이 틀렸다는 근거는 없다.

최소 수정: 공통 오류·실제 연결 정리만 공유하고, 각 사례의 `beforeEach`에 해당 실패 주입을 직접 쓴다. `stage`를 실행 함수 표로 바꾸는 공통화는 하지 않는다. 기존 spec 안에서 수정한다.

검증: 세 사례 모두 최초 오류 객체를 그대로 던지고 실제 연결을 닫는지 유지한다. 정리 실패 사례도 실제 `close`를 수행한 뒤 실패를 주입한다. common 전체 테스트·커버리지와 lint를 확인한다.

### C2. NATS fixture의 장애 준비 절차 분리

- [ ] [nats-pubsub.service.spec.ts](../libs/common/src/nats/__tests__/nats-pubsub.service.spec.ts)의 478행부터 시작하는 세 실패 사례를 각각의 `describe`로 나눈다.

조건·근거: `stage`와 context 생성 순번이 두 번째 앱 생성 실패, 첫 연결의 `flush` 실패, 첫 앱 정리 실패를 결정한다. 490·496·499행의 분기에 더해 511행에서는 같은 `stage`로 기대 context 수까지 계산한다.

영향: 테스트 설명만으로는 어느 앱이 만들어지고 어느 연결·정리 작업이 실패하는지 확인하기 어렵다. 장애 주입과 기대값이 같은 선택 변수에 결합되어 있다. 실행 오류를 확인한 것은 아니다.

최소 수정: 세 사례에서 실패할 호출과 생성될 앱 수를 직접 드러낸다. 실제 앱 생성·정리의 공통 준비만 공유하고, 모든 앱을 정리하며 최초 오류를 보존하는 단언은 유지한다.

검증: 두 번째 앱 생성 실패에서는 먼저 만든 앱 하나를, `flush` 실패 두 사례에서는 앱 둘을 각각 닫는다. 정리 실패가 최초 초기화 오류를 덮지 않아야 한다. common 전체 테스트·커버리지와 lint를 확인한다.

`git ls-files`의 619개 중 616개의 내용을 검토했다. 제외한 것은 바이너리 fixture인 `apps/api/api-docs/assets/image.png`, `apps/api/src/__tests__/helpers/assets/image.file`과 `pnpm-lock.yaml`의 자동 생성 의존성 해석 데이터다. lockfile의 생성 구조와 선언 파일·설치 명령의 연결은 확인했다. 저장소 밖의 의존성 구현과 무시된 빌드 산출물은 대상에 포함하지 않았다. 제외 대상을 뺀 미검토 파일은 없다.

파일 내용과 호출 경로를 읽고, 보조 검사로 JS·TS 계열 516개 파일의 AST를 파싱했다. 구문 진단은 없었다. 사용자 홈의 메시지 선택식은 실제 `ApiError`를 사용해 `ApiError`, `Error`, `TypeError`, 문자열, null, undefined, 일반 객체의 7개 입력에서 기존 식과 단순화한 식의 결과가 같음을 확인했다. 이는 브라우저 장애 재현이 아니다.

`pnpm run lint:root`의 루트 코드·전체 서식·문서 링크·셸 검사를 통과했다. 기본 링크 검사에서 제외되는 TODO 문서는 로컬 링크 15개의 대상 파일 존재 여부를 별도로 확인했다.

BFF의 인증 상태 처리, 구매 workflow의 상태 전환, Redis 정리 범위, benchmark의 실행 모드와 CI matrix는 실제 계약·실행 조건을 표현하므로 이 항목에 포함하지 않았다. 테스트 입력·기대 데이터만 달라지는 `each`, 비동기 완료 확인, 오류를 주입할 호출 순번 판별도 같은 기준으로 구분했다.

운영 코드·테스트·실행 설정은 수정하지 않았다. 전체 테스트·빌드·E2E·race·benchmark는 변경 없는 구조 검토이므로 이번 검토에서 다시 실행하지 않았다. 기존 인증 결함과 미결 정책은 [인증 TODO](authentication.md)에 남아 있다.
