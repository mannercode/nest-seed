# 파일 관리

현재 [AssetsService](../apps/api/src/services/infrastructure/assets/assets.service.ts)가 presigned 업로드·소유 부여·다운로드 URL·삭제·만료 정리를 맡고, [MoviesService](../apps/api/src/services/core/movies/movies.service.ts)가 이미지 요청·완료 확인·영화 연결을 조합한다. 같은 소유자의 finalize 재시도와 영화 연결 실패 후 재시도는 이미 테스트가 있다.

## F1. 재사용할 파일 API와 접근 정책 — 결정 필요

- [ ] 영화 이미지 외에 제공할 첫 사용처와 업로드·조회·다운로드·삭제 권한을 정하고 공통 파일 계약을 구성한다.

근거: 현재 HTTP 업로드·확정·삭제는 관리자용 영화 경로에 있다. [Asset 모델](../apps/api/src/services/infrastructure/assets/models/asset.ts)은 연결 대상만 저장하며 업로더·공개 범위는 저장하지 않는다. 자산 조회는 다운로드 URL을 함께 생성한다.

최소 범위: 사용자 프로필이나 비공개 첨부를 지원할지, 업로드 요청자와 연결 대상의 관계, 미확정 파일의 관리 권한, 단일 소유 유지 여부를 정한다. 다운로드 URL 발급 전의 인가와 이미 발급한 URL의 유효 기간을 구분한다. 저장소 연동은 `libs/common`, 앱의 파일 정책과 업무 대상 연결은 기존 SoLA 경계에서 소유한다.

검증: 미인증·소유자·다른 사용자·관리자의 요청별 허용 범위를 확인한다. 비공개 파일을 지원하면 타인에게 URL을 발급하지 않고, 만료·삭제 후 다운로드가 정해진 결과를 반환한다. 인가 검증은 [권한 R2](authorization.md)와 함께 수행한다.

## F2. 업로드 확정의 책임과 동시 삭제 — 검증 우선

- [ ] 업로드 완료 확인·소유 부여·대상 연결의 책임을 확정하고, finalize와 파일·대상 삭제가 겹치는 경우를 재현한다.

근거: `AssetsService.finalizeUpload`는 소유 부여를 처리하고 실제 업로드 확인은 `MoviesService`가 먼저 호출한다. 소유 부여·영화 연결·pending 제거는 여러 DB 작업이다. 기존 동시 finalize 테스트는 중복 연결을 막는지 확인하며 일부 경쟁 응답의 404를 허용한다.

최소 범위: 새 소비자가 업로드 확인을 빠뜨리지 않도록 완료 계약의 소유 지점을 정한다. 삭제된 파일의 재연결이나 삭제된 대상에 소유만 남는 경로가 있는지 확인한다. 동시 finalize의 응답을 바꿀 필요가 있으면 기존 204·404 계약부터 결정한다.

검증: 저장 단계 사이에서 실행 순서를 제어해 finalize 대 파일 삭제·대상 삭제를 확인한다. DB의 소유·연결·pending과 실제 S3 객체가 함께 일관된 상태로 끝나며 기존 재시도 계약을 유지한다.

## F3. 삭제 중 실패와 늦게 끝난 업로드 — 검증 우선

- [ ] S3·DB·대상 연결의 삭제 중 실패와 발급된 업로드 요청의 뒤늦은 완료를 재현하고 삭제 완료·재시도 계약을 정리한다.

근거: 자산 삭제는 S3 삭제 후 DB 삭제이고, 영화의 개별 파일 삭제는 연결·pending을 먼저 제거한다. S3 실패 시 자산 DB 행은 남지만 이미 확정된 자산은 미완료 업로드 정리의 대상이 아니다. 업로드 요청을 발급한 뒤 파일을 삭제하는 경로도 있다.

최소 범위: S3 일부 성공 후 실패, S3 성공 후 DB 실패, 연결 제거 뒤 실패한 요청의 재시도를 확인한다. 아직 유효한 presigned 요청으로 삭제 후 같은 key에 업로드할 때 잔여 객체가 생기는지도 확인한다. 재시도 주체·삭제 상태 보존·물리 삭제 시점은 재현 결과에 따라 결정한다.

검증: 재요청이 남은 삭제를 완료하고 다른 소유자의 파일은 유지한다. 삭제 후 업로드가 완료되어도 추적·정리할 수 있는 계약을 검증한다. 실패를 성공 응답으로 바꾸지 않는다.

## F4. 만료 업로드와 남은 연결 정보 정리 — 검증 우선

- [ ] 만료 업로드 정리 뒤 남는 pending 관계를 확인하고, 실패한 정리의 재실행과 finalize 경합을 검증한다.

근거: 자산 정리는 만료된 무소유 자산만 조회하며 [영화 pending 저장소](../apps/api/src/services/core/movies/movie-pending-assets.repository.ts)를 갱신하지 않는다. 현재 정리는 대상 전체를 읽고 5분짜리 분산 락 안에서 처리한다.

최소 범위: 만료·중단된 업로드의 객체·자산 행·pending 관계를 정리할 책임을 정한다. 하위 Assets 모듈에서 Movies를 역참조하지 않는다. 처리 도중 실패·프로세스 종료·락 만료가 발생해도 다음 실행이 이어갈 수 있는지 확인하고, 처리량 제한이 필요하면 근거와 범위를 정한다.

검증: 만료·소유 부여의 경계, 일부 삭제 실패 후 재실행, 두 실행의 중첩을 제어해 확인한다. 완료된 파일은 보존하고 정리된 업로드의 활성 pending 관계는 남지 않는다.

## F5. 파일 크기·형식과 보관 조건 — 결정 필요

- [ ] 지원할 파일의 크기 상한·형식·다운로드 방식을 정하고 업로드 요청과 스토리지 조건에 반영한다.

근거: [CreateAssetSchema](../apps/api/src/services/infrastructure/assets/dtos/create-asset.dto.ts)는 크기를 양의 정수로만 제한하고, 영화 서비스는 신고한 MIME의 `image/` 접두사를 확인한다. [S3 연동](../libs/common/src/s3/s3-object.service.ts)은 신고한 크기·Content-Type·체크섬을 업로드 조건으로 사용하며 실제 파일 형식을 판별하지 않는다.

최소 범위: 신고값의 일치 확인과 실제 내용 검사 중 어디까지 보장할지 정한다. 브라우저 표시·첨부 다운로드와 파일명 처리도 지원 형식에 맞춘다. 사용자별 할당량·악성 파일 검사·대용량 분할 업로드는 사용처와 운영 수단이 정해진 경우에 별도 범위로 잡는다.

검증: 허용·거절 경계의 크기와 형식, 누락·변조된 업로드 필드, 체크섬 불일치, 만료 요청을 확인한다. 실제 내용 검사를 선택하면 신고 MIME만 바꾼 파일도 검증한다.

검증 위치: [assets.spec.ts](../apps/api/src/__tests__/infrastructure/assets.spec.ts), [movies-assets.spec.ts](../apps/api/src/__tests__/core/movies-assets.spec.ts), [S3 테스트](../libs/common/src/s3/__tests__/s3-object.service.spec.ts). DB 상태와 실제 업로드·다운로드 결과를 함께 확인한다.
