# 프로젝트 전체 리뷰

정기 리뷰와 저장소 전체 검토에 적용한다. 수정 가치는 [README의 영역별 변경·검토 기준](../../README.md#기능코드-변경-시-주의사항)으로 판단한다. 시드 구성은 읽기·유지 부담을 함께 평가하고, 여러 프로젝트에서 재사용하는 `libs/`는 공개 계약과 재사용 정확성을 기준으로 삼는다. 앱의 사용 여부만으로 라이브러리 기능을 불필요하다고 판단하지 않는다.

## 검토 범위와 진행

전체 리뷰는 diff 유무와 관계없이 현재 저장소 전체를 대상으로 한다. 기준 커밋과 미커밋 변경 여부를 먼저 확인한다.

- `git ls-files`를 기준으로 파일 목록을 확인하고 작업 범위의 미추적 소스·설정도 포함한다. 소스·테스트뿐 아니라 루트와 숨김 설정, CI, 개발 환경, 인프라, 실행 도구, 의존성 선언·lockfile, 문서와 파일·폴더 배치를 검토한다.
- 파일 내용과 함께 호출·import·설정 주입·실행 경로를 연결해 확인한다. 영역별 규칙은 [README의 안내 문서](../../README.md#구조와-선택)와 [개발 규칙](conventions.md)을 따른다.
- 검토한 파일과 남은 범위를 추적한다. 외부 의존성·생성물 등 직접 검토에서 제외한 대상은 범위와 이유를 명시한다. `docs/backup/`은 과거 원문 보관본으로 구분하고 현재 구현 지침으로 적용하거나 내용을 갱신하지 않는다.

## 점검 항목

| 항목                   | 확인할 내용                                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 이름과 역할            | 클래스·함수·파일명이 실제 책임을 설명하는가? 같은 역할에 다른 명명 규칙을 쓰거나, 이름보다 많은 일을 하는가?              |
| 책임과 의존성          | SoLA 경계와 공개 진입점을 지키는가? 순환참조, 내부 구현 직접 참조, 책임 중복이 있는가?                                    |
| 파일·폴더 배치         | 관련 코드를 자연스럽게 찾을 수 있는가? 불필요한 파일 분할이나 한 파일에 뒤섞인 책임이 있는가?                             |
| 복잡성과 불필요한 요소 | 추상화·분기·중복·fallback이 현재 요구와 공개 계약에 필요한가? 사용하지 않는 코드와 설정이 남아 있는가?                    |
| 계약과 실패 처리       | 타입·스키마·실제 반환값이 일치하는가? 명시한 정합성을 지키며, 실패·부분 초기화·종료 때 자원과 진행 중 작업을 정리하는가?  |
| 설정과 의존성          | 설정이 실제로 적용되는가? 기본값·env·버전 선언이 충돌하거나 중복되는가? 의존성 분류와 공개 export의 소유 위치가 적절한가? |
| 실행 경로와 CI         | 문서대로 개발·빌드·검증할 수 있는가? 로컬과 CI가 의도한 검사 범위를 실행하며, 실패와 정리 오류가 종료 코드에 반영되는가?  |
| 문서와 주석            | 현재 동작·보장·한계를 정확히 설명하는가? 잘못된 주석, 오래된 명령·링크, 중복 설명, 불필요한 작업 이력이 있는가?           |

## 테스트 이름·구조·단언

모든 영역의 테스트를 [테스트 작성 규칙](conventions.md#테스트는-한-행동의-결과를-검증한다)에 따라 확인한다.

- `describe`의 조건과 `it`의 제목을 이어 읽으면 어떤 동작과 결과를 검증하는지 알 수 있는가? 테스트 구성·관측 방법의 나열, 모호한 표현, 코드와 어긋난 설명은 없는가?
- 조건 준비는 해당 `beforeEach`에, 검증할 동작과 결과 단언은 `it`에 있는가? 보조 함수의 위치와 자원 정리도 기존 테스트 패턴을 따르는가?
- 실제 단언이 제목의 보장을 뒷받침하는가? 처리 완료 전의 일시적인 관측, 빈 배열·누락된 값도 통과하는 검사, 단일 프로세스 검증을 분산 보장처럼 표현한 설명은 없는가?

## 발견 사항과 완료 보고

발견 사항마다 위치·발생 조건·실제 영향·근거를 적고, 코드로 확인한 사실과 실제 재현한 결과를 구분한다. 최소 수정 범위·필요한 검증과 수정으로 늘어나는 읽기·유지 부담을 함께 판단한다. 현재 요구사항 안에서 바로 수정할 오류, 계약·범위 결정이 필요한 변경, 보류할 항목을 구분한다.

완료 보고에는 다음을 명시한다.

- 기준 커밋과 검토한 미커밋 변경, 영역별 검토 범위, 제외 대상과 이유, 미검토 범위
- 실제 실행한 검사와 결과, 실행하지 못한 검사와 이유
- 남은 오류·미결 판단·보류 항목과 위치

검토 범위가 남아 있으면 전체 리뷰 완료로 보고하지 않는다. 검색·표본 검토·테스트 통과만으로 모든 파일의 검토를 대신하지 않는다. 리뷰 완료와 발견 사항의 수정 완료도 구분한다.

실제 발견 사항과 미완료 작업은 루트 `_todo/`에서 관리하고, 완료 항목은 [README의 관리 원칙](../../README.md#기능코드-변경-시-주의사항)에 따라 삭제한다. 이 문서에는 반복해서 적용할 기준만 둔다.
