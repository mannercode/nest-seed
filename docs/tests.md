# tests/ — 배포 스택 대상 테스트

앱·라이브러리의 단위·통합 테스트는 각 workspace에 둔다. `tests/`는 실제로 배포된 스택을 프로세스 밖에서 검증해야 의미가 있는 테스트만 모은다. 실행 명령과 산출물 위치는 [`tests/README.md`](../tests/README.md)가 소유한다.

## 1. api-race — 다중 복제본 경합

프로세스 하나의 통합 테스트로는 서로 다른 API 복제본이 같은 자원을 동시에 건드리는 순간을 제대로 만들 수 없다. race 테스트는 다중 복제본 스택에 HTTP/SSE 요청을 동시에 보내 다음 보장을 검증한다.

- 같은 자원의 상태 전이는 승자를 하나만 남긴다.
- 중복 HTTP 요청은 같은 결과로 수렴하고 별도의 부수 효과를 만들지 않는다.
- 한 복제본이 종료되어도 다른 복제본이 요청과 durable 작업을 이어간다.
- 한 복제본에서 발생한 이벤트가 다른 복제본에 붙은 SSE 클라이언트에도 전달된다.

요청이 여러 복제본에 실제로 분산됐는지를 `x-replica-id`로 확인한다. 이 조건이 없으면 요청이 사실상 한 프로세스에서만 실행된 거짓 성공이 될 수 있다. 락은 경쟁 비용을 줄이는 도구일 뿐이고, 정합성은 DB의 원자 전이·CAS·트랜잭션이 보장해야 한다는 것도 이 테스트 계층의 핵심이다.

```text
같은 자원에 대한 동시 요청 A → api-1, B → api-1   프로세스 간 경쟁을 증명하지 못함
같은 자원에 대한 동시 요청 A → api-1, B → api-2   프로세스 간 경쟁을 검증할 조건을 충족
```

## 2. api-benchmark — 회귀 비교

벤치마크는 절대 성능 인증이 아니라 **같은 머신·같은 조건의 이전 결과와 비교**하는 회귀 도구다. 읽기와 쓰기를 따로 측정한 결과와 함께 실행한 결과를 비교해 자원 경합을 본다.

결과를 볼 때는 지연 시간보다 응답 상태를 먼저 확인한다. 연결 실패나 5xx가 섞인 수치는 정상 처리 성능을 측정한 것이 아니다. 머신·이미지·데이터 조건이 다른 결과끼리도 직접 비교하지 않는다.

## 3. web — BFF 계약과 브라우저 E2E

web 테스트는 두 계층으로 나뉜다.

- 빠른 계약 테스트는 브라우저 없이 두 Next.js BFF에 같은 origin·proxy·cookie 보안 규칙이 적용되는지 검증한다.
- 브라우저 E2E는 개발 서버가 아닌 production build로 관리자·사용자 흐름과 세션 회전을 검증한다.

이 분리는 BFF의 순수한 보안 계약을 빠르게 검증하면서도, 번들·라우팅·쿠키가 실제 브라우저에서 함께 동작하는지를 놓치지 않게 한다. 운영 배포의 BFF 신뢰 경계는 [deploy 문서](deploy.md#3-프런트엔드-bff와-클라이언트-ip-경계)가 소유한다.

## 4. CI 반복 — test-stability

한 번의 성공은 레이스와 타이밍 문제의 안전을 증명하지 못한다. Stability CI는 같은 바이너리와 시나리오를 반복해 간헐 실패를 드러낸다. 반복 횟수·스케줄·timeout은 워크플로의 운영 값이므로 문서에 복제하지 않는다.

분산 시나리오는 반복 안에서 이미지를 다시 빌드하지 않는다. 같은 바이너리의 흔들림을 측정해야 하므로 빌드 시간이나 외부 레지스트리 장애를 매 회차 재측정하지 않는다.
